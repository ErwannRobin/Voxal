How a Voxal room is wired

Three planes, drawn from src/main.js. Signalling is a star through the host. Audio is a full mesh, peer to peer, always — no media server touches it under any setting. Camera and screen are their own meshes, and are the only thing that may move to a relay when a room grows.

Signalling — starDataConnection to the host. Room code = the host's PeerJS id.
Audio — mesh, alwaysOpus 32 kbps. Direct, or TURN-relayed. Never decoded by a server.
Video — mesh, then SFUPeer to peer up to 2 people; above that the default routes it through Cloudflare.

The main case

2–N participants · voice only

A simple voice room

One person creates a room and becomes the host. The room code is their PeerJS id, so there is nothing to look up. Everyone else connects to the host for control, and to each other for sound.

A heavier case

2 participants · camera + screen

Video between two peers

Nothing about the room changes. Turning a camera on adds a second, entirely separate MediaConnection set — it does not ride the audio one, and it does not renegotiate it.

The function is pure — no network, no DOM — and can only return sfu when the preference is Allow relay. If no SFU is configured on the deployment, every row falls back to P2P with sfu-unavailable. Audio is never passed through this function at all.

Where the mesh breaks

3+ participants · camera + screen

Video with more than two

Above two people, a video mesh costs each publisher one full upload per viewer. This is the one place Voxal will move media onto a server — and it moves the picture only.

The relay is not the TURN relay. A TURN server forwards opaque encrypted DTLS-SRTP and cannot decode it. An SFU decrypts media in order to forward it selectively — so with the default Allow relay setting, camera and screen in a room of three or more can technically be seen by Cloudflare. A ☁ Relayed badge appears on those tiles. Voice is never affected under any setting.
